# AI Editor URL import

The "AI Editor" tab imports a live website by URL: the backend fetches the page, stores it as a new project's single `index.html`, then the user edits it via the normal AI chat workspace. Imports must NOT trigger auto-generation (unlike a fresh new project — do not seed the initial-prompt sessionStorage).

## Asset rewriting is REQUIRED, not cosmetic
The preview iframe strips relative `link`/`script` refs and inlines only local css/js. So imported pages render correctly only if their asset URLs are rewritten to ABSOLUTE on import (the preview keeps external/absolute refs). Keep absolutizing href/src/srcset/etc. whenever touching import.

## Two safety constraints that are easy to regress
1. **SSRF DNS-rebinding:** validating a host's IP *before* the fetch is not enough — the host can resolve to a public IP at validation time and a private IP at connect time. The connection itself must be pinned to an IP that is re-validated at connect time (reject private/link-local/CGNAT ranges). Keep the literal-IP/localhost prechecks and per-redirect-hop revalidation as defense in depth.
   **Why:** otherwise internal services and cloud metadata (169.254.169.254) are reachable from a user-supplied URL.
2. **Active JS in the preview iframe:** the preview runs with `allow-scripts`. Removing `<script>` tags is NOT sufficient on its own. The full set of vectors that must also be neutralized: inline `on*` event-handler attributes, `javascript:`/`vbscript:` URLs in any URL attribute, `data:text/html` document sources, and `srcdoc` (it embeds a whole scriptable document). New active-JS sinks creep in over time — sanitize on a parsed DOM, not with regex, so quoted/unquoted/entity-encoded variants are all handled.
   **Why:** imported third-party markup is untrusted; any surviving vector executes in the sandboxed preview.

## Imported sites render via the preview's de-lazy pass
Imported WordPress/Elementor pages ship lazy-loaded images: real URL in `data-src`/`data-srcset`, `src` is a 1x1 placeholder gif, and a `.lazyload` class holds them at `opacity:0` until the site's lazy-loader JS swaps them — which usually does NOT run in our sandbox, so images/quote-cards stay blank. `buildPreviewHtml` fixes this at render time: for any `<img>`/`<source>` carrying `data-src*`, strip the placeholder `src`/`srcset` (quoted or unquoted) FIRST, then rename `data-src*`→`src*`, and force `.lazyload{opacity:1}`. Strip-before-rename matters or a duplicate `src` survives and the browser keeps the placeholder. No-op for generated apps (they don't use `data-src`).

## Escaped `<noscript>` fallbacks print as visible text (img AND tracking iframe)
`<noscript>` bodies are JS-disabled fallbacks (lazy-img copies, GTM/analytics hidden `<iframe>`, etc.). cheerio/parse5 parse a noscript body as a single raw TEXT node, so the importer's old "unwrap but keep contents" turned that markup into ESCAPED text (`&lt;img...&gt;`, `&lt;iframe...&gt;`) that the browser prints as visible tags. **Fix (canonical):** the importer now does `$("noscript").remove()` — correct because the preview runs `allow-scripts`, so noscript should never render. **Fix (migration, for already-imported projects):** `buildPreviewHtml` strips escaped `&lt;img...&gt;` (scoped to `lazyload`) and escaped `&lt;iframe...&lt;/iframe&gt;` (scoped to tracker hosts / hidden / zero-size), so legit escaped code a generated app displays is left alone. **Why scoped:** unscoped stripping would nuke instructional escaped-code snippets. Symptoms users report: "I see `<img .../>` text under the images" / "I see `<iframe googletagmanager...>` text on the page."

## Preview link behavior: same-site in-frame, external new-tab
The preview iframe is `allow-popups allow-popups-to-escape-sandbox`. `buildPreviewHtml` injects a click handler that makes it browser-like: it detects the imported site's primary host (most-frequent `href="https://HOST"`), then on anchor clicks navigates SAME-host links inside the preview (default, stays in the one frame) and opens OTHER-host links (WhatsApp/wa.me, booking, socials) in a real new tab via `window.open`. In-page `#anchors` and `mailto:`/`tel:` keep default behavior. **Why:** external sites refuse to render in a frame (X-Frame-Options/CSP) so they can't stay "in the same preview"; forcing ALL external links to new tabs (an earlier attempt) was wrong — the user wants the distinction.

## Imported live sites are inherently slow/flaky in preview — set expectations
A real WP import pulls ~100+ external assets from the live domain on every render, and its main stylesheet is render-blocking (e.g. ~700KB). The iframe paints WHITE until that CSS loads (~1.5-2s), and theme JS (Astra mobile menu, etc.) needs its external scripts loaded before it works — so "the hamburger doesn't work right after refresh, then works a moment later" is expected, not a bug we can fully fix. The reliably fixable part is image rendering (de-lazy above). Offer regeneration as the clean alternative.

## Stripped theme JS (hamburger menu) re-implemented in preview — IMPORTED-ONLY
Imported themes ship a hamburger + a hidden dropdown nav, but their toggle JS (Elementor, etc.) is stripped on import, so tapping does nothing. `buildPreviewHtml` injects a generic toggle: on a hamburger-class click, resolve the menu (aria-controls → Elementor `nav.elementor-nav-menu--dropdown` in the same widget → nearest nav/menu) and force it open/closed with inline `!important` styles. **Why gated:** the handler is a document capture-phase listener; running it on GENERATED apps would hijack their own working menu/control JS. So `buildPreviewHtml(files, isImported)` injects it ONLY when imported (detected via `project.description` starting with `"Imported from"`). **Keep it safe:** match only real hamburger CLASSES (no generic `button[aria-controls]`/`[aria-label*=menu]`), validate the resolved target is NAV/UL/menu-like before acting, and never `stopPropagation` (so a real control's own handler can still run). Same lesson applies to any future "re-implement stripped behavior" preview shim: gate to imports + validate target + don't swallow events.

## Multi-page import: crawl the whole site, navigate ONE page at a time
Import is multi-page: the server BFS-crawls the site (bounded by a max-pages cap + small concurrency) and stores one `.html` file per page — homepage→`index.html`, every other page keyed by a path→slug normalizer (`pageKeyFromPath`). The client preview renders ONE page at a time into the sandboxed srcDoc and swaps pages via `postMessage`, NOT by embedding every page.
- **Don't embed all pages in one srcDoc.** The first attempt embedded every page's processed HTML + did in-place `documentElement` swaps; for a real WP site that's ~5.7MB of srcDoc and the iframe renders BLANK. The working design keeps srcDoc to a single page: a tiny injected router intercepts a same-site link, posts `{__buildlyNav:"<key>.html"}` to the parent, the parent validates (`e.source===iframe` AND `/^[a-zA-Z0-9._-]+\.html$/`) and sets `previewPage` state → iframe re-renders to that page. `buildPreviewHtml(files,isImported,currentPage)`; `previewPage` resets on project change.
- **The router MUST apply the same same-host guard as `linkHandler`.** Gating only on "key exists in stored pages" is a bug: an external link whose path collides with a stored key (classic: a footer credit `https://other.tld/` → path `/` → `index.html`, which always exists) gets hijacked into the preview instead of opening a new tab. Intercept only when `norm(u.hostname)===norm(primaryHost)`; let everything else fall through to `linkHandler`.
- **Client `key()` must mirror server `pageKeyFromPath` exactly** (same decode/strip-ext/slug rules) or clicks compute a filename that isn't in the stored set and silently fall through to default nav.
- **Known limitations (acceptable tradeoffs, not bugs):** (a) the max-pages cap truncates very large sites — fine for typical brochure sites, which fit fully; (b) two distinct paths that normalize to the same key collide and the second is dropped (rare; e.g. transliterated/non-ASCII paths). Fixing (b) for navigation would need a path→key map embedded client-side, re-bloating srcDoc — not worth it for the edge case. (c) Slow first paint: a heavy imported page can take ~3-4s to render — an immediate screenshot looks blank but it's just timing; verify with a real browser test that waits.

## Regeneration reuses the imported site's real images
When the user regenerates an imported site into a clean app, the generation system prompt (`buildSystemPrompt`) must tell the model to REUSE the real absolute image URLs already present in the imported HTML (img src / source srcset / CSS background-image) and compose them into the new design. **Why non-obvious:** the prompt has two rules that otherwise forbid this — the REFERENCE-IMAGES "never hotlink external asset URLs" line and the RUNTIME-ROBUSTNESS "no external image URLs that may 404" line. Both must keep an explicit EXCEPTION pointing at the IMPORTED WEBSITE ASSETS section, or the model strips the photos and the result no longer feels like the same site. Keep the three in sync if any is reworded.

## Gotcha
Scheme checks must normalize first (strip control/whitespace chars, lowercase) before comparing, or `java\tscript:` / entity-encoded schemes slip through.

## A large multi-page import blows the model's input-token limit
A 30-page imported site is multiple MB of HTML (e.g. ~5.45M chars ≈ 1.6M tokens), and `buildFileContext` used to inline EVERY file verbatim into the system prompt — so any adjustment to such a project hard-failed with OpenAI `context_length_exceeded` (400) and the UI showed "Something went wrong while building your app". Fix: `buildFileContext` caps total at `MAX_FILE_CONTEXT_CHARS` (~2M chars, ~3.4 chars/token for dense HTML), ordering index.html → css → js → remaining pages smallest-first, and returns `{ context, omitted }`. **Critical integrity rule:** any page OMITTED from context must be protected server-side — `persistGeneratedFiles` takes a `protectedPaths` set and skips writes to those paths, because the model never saw their real content and any output for them would be a corrupting guess. The prompt NOTE also tells the model not to output/recreate omitted pages, but the server guard is the real safety net. **Why non-obvious:** char-budget is only an estimate; conversation history also counts toward the limit, but history stores explanation-only (not code) so files dominate.

## Regeneration must rebuild the WHOLE site, every nav tab, not just the homepage
Users expect a regenerated import to become a complete multi-view single-page app with a finished, well-designed tab for EVERY primary nav section (home + each service/about/pricing/blog/contact), images placed like a designer — not just a polished homepage with empty/stub tabs. This lives in the IMPORTED WEBSITE ASSETS section of `buildSystemPrompt`. **Subtlety:** it must coexist with the omitted-files NOTE from `buildFileContext` — that NOTE forbids emitting code blocks for omitted page FILES (their content was never shown), but the model MAY still build an in-app tab/view for that section inside index.html with on-brand content. Keep the two worded so they don't read as contradictory (file-level protection vs. view-level rebuild).

## Reject empty/blocked imports instead of creating a blank project
Bot-protected or JS-only sites hand back a shell with an empty `<body>` (e.g. an HTTP 202 challenge of ~168 bytes); `prepareImportedHtml` strips it to `<html><head>..</head><body></body></html>`. The import used to insert that as a project, so the preview showed NOTHING with no explanation — and the import response even reported `fileCount:1`. Fix: after `crawlSite`, the import route computes `meaningfulContentScore(html)` (visible body text length + media count*50 + structural-element count*25) across all crawled pages and, if the best score is below `MIN_IMPORT_CONTENT_SCORE` (80), returns HTTP 422 with a Dutch "couldn't import / blocked or JS-rendered" message instead of inserting anything. **Why non-obvious:** the same site can succeed earlier and fail later — protection kicks in after repeated rapid imports, so this is intermittent and not a code regression. The frontend (ai-editor.tsx import handler) already surfaces the server `error` string, so keep that message Dutch + user-facing.

## Imported-site mobile menu: build our own overlay, don't force the theme's menu open
For IMPORTED sites the preview re-implements the hamburger (the theme's toggle JS was stripped on import). Forcing the theme's own mobile menu visible (display/visibility/opacity !important) rendered it CLIPPED off the right edge on real themes — nav text cut off, unreadable. **Fix:** on hamburger click, COLLECT the theme menu's `<a href>` links and render our OWN controlled overlay (fixed inset:0 backdrop + right panel `width:min(340px,85vw)`, links with `white-space:normal;word-break:break-word` so text can never be clipped; close via X/backdrop/Escape; re-click toggles). Keep original href on the new `<a>` so the existing capture-phase router/linkHandler still drive same-site nav + external new-tab. **Why:** theme CSS is unpredictable; reusing their hidden menu inherits their broken positioning. Owning the overlay sidesteps all theme-specific layout breakage. **Gotchas:** only `preventDefault()` AFTER findMenu resolves (else you swallow clicks on working/unrelated controls); skip links with empty href; gate to imported sites only (generated apps ship working menu JS). **Untestable via Playwright:** preview iframe sandbox has no allow-same-origin, so e2e can't reach inside — verify injected-string escaping in the written file instead.

## Regex backslashes inside the injected-script TEMPLATE LITERAL must be double-escaped
Any regex written into the preview's injected `<script>` (a backtick template literal in project-workspace.tsx) loses single backslashes: `` `\s` `` evaluates to `"s"` (a `\` before an ordinary char is a legal NonEscapeCharacter and is dropped), so `/\s+/g` shipped to the runtime as `/s+/g`. That silently corrupted menu labels — `Lesrooster en contact` → `Le roo ter en contact` (every "s" collapsed to a space). **Rule:** write `\\s` (and any `\d`, `\w`, etc.) in the .tsx source so the runtime string contains `\s`. **Why this hid:** it looks like a font/glyph rendering bug, not an escaping bug — the symptom is missing letters, and the source "looks" like a correct regex. **How to verify:** there is no same-origin e2e access to the sandboxed preview, so eval the template literal in node and assert the produced string contains `\s`, then run the real label through it. Defense-in-depth also added: overlay text nodes force a complete system font with inline `!important` so a hostile theme webfont can't bleed in — but that was NOT the primary cause here.
